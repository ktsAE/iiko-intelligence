# What the manager can ask

v0.7.1 exposes 28 MCP tools (26 reads, 2 writes) for one organization. A configured profile allows the connector to try each live report. The restaurant’s iiko permissions determine which calls succeed.

| Question | Offline reports | Live MCP |
| --- | --- | --- |
| What data can I access? | `get_capabilities` and `get_data_status` describe the saved dataset. | `check_live_access` runs queries for sales, catalog, stock and documents. It samples a dish and warehouse for recipe and cost calls. You can supply specific IDs. A document detail needs a document ID from its list. |
| What sold and which dishes explain a change? | `get_sales_summary`, `get_top_dishes` and `compare_sales_periods` accept `source="snapshot"` for an imported period. | The same tools query SALES OLAP when Cloud is configured. Pass a named calendar period in both dates, or give an inclusive range. The default scope is the authorized organization. An exact `department` narrows the report to one outlet. |
| What goes into a salad? | No restaurant recipe | `find_iiko_products` finds the dish. `get_recipe_card` reads the card effective on a date, including ingredients, gross and net quantities, yield and preparation text where available. |
| How much does it cost? | Demo costs only | `get_item_cost` reads iiko's accounting cost for a product, quantity, warehouse and time. `get_recipe_cost` calculates ingredient cost for the recipe yield and per output unit from the flattened recipe and the selected warehouse's unit prices. Missing or ambiguous prices prevent a total. This calculation excludes labour and overhead. |
| What is on hand? | `get_stock_balances` reads an imported, dated warehouse balance. | `list_iiko_stores` finds warehouses. `get_live_stock` queries quantity and value by warehouse, product and timestamp. iiko returns rows with nonzero quantity or value. |
| What postings can reconcile prepayments? | No local posting dataset. | Find the manager's saved OLAP report with `list_saved_iiko_reports` and `get_saved_iiko_report`. Alternatively use `list_transaction_fields` and `get_transaction_report` with confirmed accounts, amount fields and reference groupings. |
| What did the team count? | No stocktake documents | `get_inventory_counts` lists inventory documents. `get_iiko_document` reads their count lines and first-stage lines. Surpluses and shortages are reported when supplied by iiko. |
| What deliveries arrived? | `get_purchases` summarizes imported posted invoice headers. | `get_incoming_invoices` lists documents. `get_iiko_document` reads quantities, prices and VAT fields. |
| What did we write off? | `get_writeoffs` summarizes imported posted act headers. | `get_writeoff_acts` lists documents. `get_iiko_document` reads product quantities and units. |

Sales are the iiko «Сумма со скидкой» amount by «Учетный день». Sales and warehouse document lists accept up to 366 inclusive days per request. The connector resolves named periods using the restaurant calendar, then requests at most 31 days at a time. Sales use explicit `CUSTOM` filters. Exact dates can be ISO or DD.MM.YYYY. A week runs Monday–Sunday. Current week/month/quarter/year run through today. `last_N_days` includes today and `last_N_complete_days` ends yesterday. `week_before_last`, `month_before_last`, `previous_week_to_date` and `previous_month_to_date` support comparisons. For the last of these, the end date is capped at the last day of the previous month. A comparison flags overlap, different lengths, open days when the local date is known, and days with no returned rows. It reads the time zone from the organization’s terminal groups. If no single zone is available, pass the outlet’s confirmed `restaurant_timezone` (for example `Europe/Moscow` or `+03:00`), or request exact dates. Explicit dates work without terminal access. If iiko returns HTTP 503 for the field list, MCP requests the sales report directly with the same authorized organization, date and outlet filters. In that case the report omits optional order counts and average order value. Reports show the returned date and currency when supplied. An empty report has no verified amount. Order count and average order value require iiko’s unique order measure. Dish details are checked against each day’s total. A Cloud HTTP error identifies the operation and status. When available the connector returns a validated correlation ID for support and a numeric Retry-After value.

Saved OLAP and transaction reports can be queried with explicit dates and the restaurant’s grouping, account and amount fields. OLAP data is grouped; read the full result before reconciling. [iiko reporting API](https://api.iiko.help/docs/en/guides/analytics-and-reports/)

## Record and table operations

`describe_iiko_records` lists the supported types and describes each action’s header and line fields. `list_iiko_records` refreshes a register from the Cloud. `get_iiko_record` reads one record and its version. `create_iiko_record` creates a record with its header and lines. `update_iiko_record` reads the selected record again, merges the requested changes and sends them to iiko. Supply `expected_version` from the read to detect changes before submission. iiko's endpoints do not all offer a server-side conditional write.

| Area | Supported records |
|---|---|
| Warehouse documents | Incoming and outgoing invoices, supplier and incoming returns, stocktakes, write-offs, internal transfers, production, disassembly, sales, transformations, substitutions |
| Financial records | Accounts, cash-flow categories, incoming and outgoing service acts |
| Catalog and pricing | Products/dishes, product groups/categories, size scales, recipe cards, counterparties, supplier and internal price lists |

For table lines use `row_edits` with `field`, `action`, `values` and a unique `match` for an edit. An array supplied in `changes` replaces that entire array. The supplier price list selector needs `counteragentId`; an internal price list needs the date it was active. A register corresponds to a supported iiko entity. The public API has no general database-table designer. Derived OLAP report rows are read by reporting methods.

The connector sends create and update operations using the saved organization's credentials. Posting, unposting, deletion and payments are separate iiko operations outside these tools. Use a new UUID `request_id` for each intended change and the same UUID to retry it. The installation keeps local operation receipts under `data`. If the response is lost, the connector returns `outcome_unknown` and the target ID when known; check iiko before sending another change. The local receipt does not synchronize requests across separate installations. [Official iiko Cloud API contract](https://api-ru.iiko.services/api-docs/docs)

The manager can ask in Russian. The local MCP client picks the methods. For example, «Найди салат “Цезарь” и покажи его техкарту на 20 ноября», «Рассчитай стоимость закладки и единицы выхода по ценам склада “Кухня”», «Открой накладную № 0128 за неделю и покажи позиции». If a name matches several dishes or warehouses, choose the right one. For stock and costing, use `now`, `end_of_yesterday` (23:59:59.999 local), or an ISO timestamp with offset. A recipe uses a single accounting date. For explicit recipe-cost timestamps use the restaurant’s offset or pass its timezone, since the card is selected by local date. Use `next_page_arguments` when returned to keep the dates or timestamp fixed across pages. Other lists provide `next_offset`. Check document status before counting posted activity. Directory names and units are current labels and can differ from historical labels.

Cloud methods use an organization-specific credential. Verify a known recipe, warehouse and document against iikoOffice on first use. The restaurant's deployment and licence determine access. The ordinary browser text report includes snapshot reports only. Classic iikoServer REST, a hosted browser connector and automatic recurring refresh have no implementation in this build.
